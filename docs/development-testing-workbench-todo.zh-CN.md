## 1. 目标与复杂度

工程师不必展开每个父工作项，就能知道：

1. 当前有哪些任务或缺陷需要自己处理。
2. 自己提交测试的工作正在等谁处理。
3. 哪些工作本轮测试通过，哪些不通过，有哪些未解决缺陷。

整体属于中等偏大的前后端改造，不是只增加几个状态或前端标签页。

| 阶段     | 交付目标                         | 相对复杂度                   |
| -------- | -------------------------------- | ---------------------------- |
| 前置核查 | 明确数据、状态语义与兼容方案     | 中                           |
| 第一阶段 | 缺陷平铺待办、父项缺陷汇总       | 中，可独立交付               |
| 第二阶段 | 提测记录、测试结论、双向交接通知 | 中高，需要数据模型与事务设计 |
| 第三阶段 | 关闭权限、阻塞校验、例外审批     | 高，可延后                   |

建议先实施前置核查和第一阶段，再做第二阶段。第一阶段只解决“哪些缺陷等我修”，不能宣称已经解决“我的提测结果跟踪”。

当前不承诺工期；完成数据核查与交互范围确认后，再估算开发、联调、回归及上线时间。

## 3. 推荐业务规则

以下为待确认的默认方案，不是当前系统强制规则。

### 3.1 类型、状态与归属

- 类型表示“是什么”，状态表示“做到哪一步”，父子关系表示“属于谁”。
- 测试发现后新建缺陷，每个可独立修复和验证的问题一条；父任务不改成缺陷类型。
- 当前任务专属缺陷可以作为子项；跨任务公共缺陷使用独立工作项和明确关联，避免重复记录。
- 一个缺陷即使有父项，也必须能独立进入处理人的待办清单。
- 发现单个缺陷不等于整轮测试结束；父项可以继续测试，子缺陷同步修复。
- “未登记缺陷”“所有缺陷关闭”“本轮测试通过”“业务验收完成”是不同概念，不自动等同。

### 3.2 人员与交接

- 第一阶段继续使用现有负责人表示当前处理人，不凭父项负责人推断子项负责人。
- 第二阶段保存提测人、指定测试人、实际测试结论提交人，避免负责人变更后丢失交付跟踪。
- 开发负责人是否单独持久化，在前置确认中决定；不能用“创建人”或“订阅人”冒充开发负责人或提测人。
- 缺陷流转建议为：待修复 -> 修复中 -> 待复测 -> 复测中 -> 验证通过；复测失败回到待修复。
- 上述名称只是业务语义，可映射到现有项目状态，例如“开发中”“待测试”“测试中”，不强制改名。

### 3.3 我的工作展示

| 区域         | 内容与入选依据                                              |
| ------------ | ----------------------------------------------------------- |
| 我的待处理   | 当前分配给自己的开发任务和待修复缺陷，提供任务/缺陷快捷切换 |
| 我的提测     | 存在本人提测记录的工作，交给测试后仍保留跟踪入口            |
| 我的待测     | 当前指定自己处理的待测或复测记录                            |
| 最近测试结果 | 与本人提测相关的明确结论，显示版本、轮次、时间和提交人      |

示例展示目标：

| 工作              | 状态   | 未解决缺陷 | 待我修复 | 测试结论     |
| ----------------- | ------ | ---------- | -------- | ------------ |
| V13 PC端设备适配  | 测试中 | 3          | 2        | 本轮尚未结束 |
| 后端新增 V13 机型 | 待测试 | 0          | 0        | 尚未测试     |
| V13 通信协议      | 待验收 | 0          | 0        | 本轮通过     |

“我的待处理”平铺展示每条缺陷，带父项来源；不复用必须展开父节点的展示规则。原“已分配/已创建/已订阅”入口保留，避免破坏现有使用习惯。

## 5. 第一阶段：先让工程师看清待办

- [ ] 增加“我的待修复”快捷入口，依据缺陷类型映射、当前负责人、待修复/修复中阶段查询。
- [ ] 子缺陷独立平铺，无论父项归谁负责、是否在当前分页、是否折叠，都不会漏掉或重复显示。
- [ ] 展示缺陷编号、标题、项目、父项来源、优先级、当前状态、负责人和更新时间；支持直达详情。
- [ ] 未分配缺陷进入项目级“待分配”清单，不伪装成任何人的待办。
- [ ] 父项展示“未解决缺陷数、待修复数、待复测数、待我修复数”，点击数字打开对应明细。
- [ ] 区分取消/重复/暂缓与验证通过；定义各类是否计入未解决和阻塞数量，不把取消当作测试通过。
- [ ] 后端分页与批量聚合，不逐个父项请求全部子项；数量与明细使用相同权限和过滤口径。
- [ ] 创建、改派、改状态、变更类型、移除父子关系、删除或恢复后，同步刷新清单与汇总。
- [ ] 保留现有列表、看板和个人筛选设置；新增中文及其他必要语言键，不硬编码翻译文本参与筛选。

阶段验收：

- [ ] 工程师无需展开 V13 父项，就能看到分配给自己的电量显示缺陷。
- [ ] 父项分配给甲、子缺陷分配给乙时，乙能独立找到缺陷，甲的个人待修复数不包含乙的工作。
- [ ] 缺陷转交测试后不再计入开发待修复；退回后重新出现，无需人工修改过滤条件。
- [ ] 分页后缺陷不丢失、不重复，汇总点击得到的明细与数字一致。

## 6. 第二阶段：提测与测试结果闭环

- [ ] 在前置核查后设计持久化提测记录：工作项、提测人、版本、环境、测试范围、指定测试人、提测时间、轮次。
- [ ] 提供“提交测试”操作；普通状态下拉改成待测试不自动伪造完整提测记录，提供补录提示。
- [ ] 提供“开始测试”“提交结论”“再次提测”操作；结论包含通过、不通过、阻塞及说明、证据、操作者、时间。
- [ ] 结论绑定具体版本和轮次；再次提测创建新轮次，保留旧轮次记录，不能覆盖历史或沿用旧版本通过结论。
- [ ] 历史任务显示“无提测记录/未记录测试结论”，不从“已完成”状态反推历史测试通过。
- [ ] 实现“我的提测”“我的待测”“最近测试结果”，当前负责人改变后仍按记录准确跟踪。
- [ ] 创建缺陷时可关联发现轮次；修复提测和复测记录能追溯验证版本。
- [ ] 明确同一工作项并发提测、重复提交、过期轮次结论和改派时的冲突策略。
- [ ] 提测记录、工作项状态和交接数据在事务中一致保存；通知在事务提交后派发，失败可重试且避免重复通知。
- [ ] 复用收件箱通知：分配缺陷、提交测试、复测退回、本轮结论；接收人按操作事件明确计算，不只依赖通用订阅。
- [ ] 通知可直达对应缺陷或测试记录；待办清单是事实来源，即使用户错过通知仍能找到工作。

阶段验收：

- [ ] 工程师提测三个任务，不必逐一打开就知道哪个等待测试、哪个不通过、哪个通过。
- [ ] 测试发现多个问题后，开发能看到独立缺陷；本轮未结束时不能误显示为“本轮测试失败/结束”。
- [ ] 修复后再次提测，旧的通过/不通过记录可查，但不会被当作当前版本结论。
- [ ] “零缺陷但未测试”和“测试通过”展示不同；有缺陷但测试仍在进行也能正确表达。
- [ ] 交接、改派、重新打开和测试通过均有可追溯记录，开发与测试使用不同账号完成全流程验证。

## 7. 第三阶段：可选强制规则

- [ ] 配置谁能提交测试结论、谁能完成业务验收；后端校验，不只隐藏按钮。
- [ ] 阻塞验收的缺陷未解决时禁止完成；区分阻塞与一般缺陷。
- [ ] 必须填写退回原因、提测版本和测试结论；明确定义 API、批量修改、拖拽的同等校验。
- [ ] 对暂缓缺陷提供接受风险记录、批准人、原因和后续安排，不通过取消缺陷绕过门禁。
- [ ] 设计项目可选启用与逐步推广，避免新规则让旧项目无法正常操作。

本轮暂不扩展：完整测试用例库、测试计划平台、通用工作流设计器、CI 自动发布、工时绩效报表。
